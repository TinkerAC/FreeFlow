# FreeFlow 毕业论文框架与写作规划

## 1. 论文定位

FreeFlow 的论文应定位为：

**偏系统开发与系统设计的本科毕业论文，算法作为链上资源检索模块中的辅助设计。**

不建议把论文写成“多平台音乐聚合播放器”，也不建议写成“推荐算法研究”或“区块链算法研究”。当前项目最稳妥的主线是：

```text
链上音乐发行与播放系统
  = 桌面端播放器
  + 创作者发布工作台
  + Web2.5 后端服务
  + IPFS/Pinata 存储
  + Solidity 访问控制与分账合约
  + 链上资源检索与排序模块
```

算法内容的作用是让论文不显得完全只是 CRUD 和界面开发。它应当作为“系统中的检索排序模块”出现，篇幅控制在 1 章或 1 个大节，不要喧宾夺主。

## 2. 优秀范文分析

本次阅读了 `papers/examples/myexample-md` 下的 6 篇范文。它们大致可以分为两类：

1. **纯系统开发型**：重点写需求分析、总体设计、数据库设计、模块实现和功能测试。
2. **算法 + 系统型**：先写算法原理、数据处理和实验，再写系统设计与实现。

FreeFlow 更接近第一类，但可以吸收第二类中“算法模块评估”的写法。

### 2.1 范文对比

| 范文 | 类型 | 论文结构特点 | 对 FreeFlow 的参考价值 |
| --- | --- | --- | --- |
| 胡孟帆《面向地研院的土地管理信息系统的设计与实现》 | 纯系统开发型 | 引言、关键技术、系统分析、系统设计、系统实现、结论 | 最适合参考章节骨架。FreeFlow 可以仿照其“系统分析 -> 系统设计 -> 系统实现”的主线 |

| 许骏亮《基于 GAN 和 FLOW 模型的仿声系统的研究与实现》 | 算法研究 + Web 系统 | 相关工作、数据处理、算法、实验、Web 前后端设计 | FreeFlow 不应照搬算法主线，但可参考实验环境、评价指标和系统展示章节 |

| 朱长泰《基于深度学习的地表建筑物识别研究与实现》 | 算法研究 + 系统落地 | 理论、模型、实验、消融、系统设计、功能测试 | 可参考图表和实验严谨性，但 FreeFlow 不需要写这么重的算法 |

### 2.2 范文共同规律

优秀论文普遍有以下规律：

1. 摘要先说明问题背景，再说明系统目标、技术路线、实现内容和结果。
2. 第一章不直接讲代码，而是讲背景、意义、现状、主要工作和论文组织。
3. 第二章集中写关键技术，避免在实现章节重复解释框架。
4. 系统类论文一定有需求分析，包括可行性、功能需求、非功能需求和业务流程。
5. 系统设计章节一定要有总体架构图、功能模块图、数据库设计图或表。
6. 系统实现章节按模块写，不按文件路径写。
7. 测试章节用表格展示测试用例，并配关键界面截图。
8. 有算法内容的论文会补充数据集、评价指标、对比实验或案例分析。

### 2.3 FreeFlow 应参考哪种写法

建议以胡孟帆和中式菜谱知识图谱两篇为主要参考：

- 胡孟帆论文提供纯系统开发型骨架。
- 中式菜谱论文提供“系统开发 + 一个智能模块”的平衡写法。

FreeFlow 的算法内容可以像中式菜谱论文中的“智能问答”一样处理：

```text
系统主体：链上音乐发行、购买、播放、评论和下载
算法模块：链上音乐资源检索与排序
```

这样答辩时可以明确说明：

“本项目本质是系统设计与实现，算法模块用于提升链上音乐资源检索质量，并不是把系统强行包装成算法研究。”

## 3. 推荐论文题目

推荐题目按稳妥程度排序：

1. **基于区块链与 IPFS 的链上音乐发行与播放系统的设计与实现**
2. **融合链上资源检索排序的音乐发行与播放系统设计与实现**
3. **基于 Web2.5 架构的链上音乐资源管理系统设计与实现**
4. **面向创作者的链上音乐发布与播放系统设计与实现**

最推荐第 1 个。它系统属性强，范围清晰，不会让老师期待复杂算法。第 2 个适合导师明确要求题目里体现算法时使用。

## 5. 各章节写作要点

### 第 1 章：绪论

本章目标是把选题讲合理，不要写技术细节。

建议内容：

- 数字音乐平台存在中心化发行、版权收益分配不透明、创作者议价能力弱等问题。
- 区块链和 IPFS 可用于资源确权、访问凭证、交易记录和内容寻址。
- 桌面音乐播放器可以提供比网页更稳定的本地播放、缓存、下载和系统集成能力。
- FreeFlow 设计一个链上音乐发行与播放系统，实现创作者发布、用户购买、播放、评论和检索。

主要工作可以写 5 点：

1. 设计并实现链上音乐系统总体架构。
2. 设计并实现创作者工作台。
3. 设计并实现 Web2.5 后端服务。
4. 设计并实现智能合约访问控制与收益分账。
5. 设计并实现链上音乐资源检索与排序模块。

#### 6.2 算法流程

```text
用户 query
  -> 查询归一化
  -> 识别 address / CID / tokenId / resourceKey
  -> SQL 候选召回
  -> 最近发布资源补充召回
  -> 身份特征评分
  -> 文本特征评分
  -> 模糊相似度评分
  -> 新鲜度评分
  -> 热度评分
  -> 总分排序
  -> 返回 reasons 和 features
```

#### 6.3 排序公式

可以写成：

```text
Score(d, q) =
  S_identity(d, q)
  + S_text(d, q)
  + S_fuzzy(d, q)
  + S_freshness(d)
  + S_popularity(d)
```

其中：

- `S_identity`：resourceKey、tokenId、合约地址、交易哈希、CID 等精确或局部匹配。
- `S_text`：标题、艺术家、专辑、流派、描述的精确、前缀、包含和分词命中。
- `S_fuzzy`：基于 Levenshtein 的归一化相似度。
- `S_freshness`：按发布时间指数衰减。
- `S_popularity`：评论数和购买数加权。

新鲜度公式：

```text
freshness = 0.5 ^ (ageDays / 45)
```

热度公式：

```text
weightedPopularity = commentCount + 3 * purchaseCount
popularity = min(1, ln(1 + weightedPopularity) / ln(31))
```

#### 6.4 评估方式

不需要做复杂机器学习实验。建议自建一个小型检索评估集即可：

- 准备 20-30 条已发布或模拟发布资源。
- 准备 30-50 个 query。
- query 类型覆盖：标题、歌手、专辑、流派、tokenId、合约地址、CID、resourceKey、错别字/拼写扰动。
- 人工标注每个 query 的目标资源或相关资源。

评价指标：

| 指标 | 用途 |
| --- | --- |
| Precision@10 | 前 10 条结果相关比例 |
| MRR | 目标资源第一次出现的位置 |
| nDCG@10 | 前 10 条排序质量 |
| Zero Result Rate | 无结果查询比例 |
| Avg Latency | 平均检索响应时间 |

对比实验：

1. SQL contains 基线。
2. 只用文本评分。
3. 文本 + 链上身份字段。
4. 完整 `chain_resource_rank_v1`。

## 8. 答辩时的算法解释口径

可以这样讲：

“本系统是偏工程实现的链上音乐系统。由于链上音乐资源除了标题和歌手，还包含 tokenId、合约地址、交易哈希、IPFS CID 等身份字段，所以普通的字符串 contains 检索不能满足需求。我设计了一个面向链上音乐资源的检索排序算法，将文本相关性、链上身份匹配、模糊相似度、新鲜度和购买/评论热度统一成一个评分模型，并返回可解释的排序原因。这个算法服务于系统中的资源检索模块。”

老师追问算法公式时：

```text
Score = 身份匹配分 + 文本匹配分 + 模糊相似度分 + 新鲜度分 + 热度分
```

老师追问复杂度时：

```text
候选召回由数据库完成，评分阶段遍历 N 个候选；
Levenshtein 相似度对文本长度做了截断，单候选近似 O(L^2)；
排序为 O(N log N)；
系统限制候选上限 500，因此工程上可控。
```

老师追问为什么不是推荐算法时：

```text
当前系统处于链上资源冷启动阶段，用户行为数据不足，因此优先实现可解释检索排序。
后续当搜索点击、播放、购买、收藏数据积累后，可以把当前热度特征扩展成个性化推荐。
```
