\chapter{链上音乐资源检索与排序模块设计}

\section{模块目标与总体设计}

链上音乐平台中的资源同时具有传统音乐信息与链上身份信息两类属性。前者包括标题、艺术家、专辑、流派和描述等元数据，后者包括链网络编号、合约地址、Token ID、发布交易哈希、IPFS内容标识以及资源唯一键等标识字段。两类属性在检索场景中的作用存在明显差异：传统元数据主要服务于歌曲发现与内容浏览，链上身份字段主要服务于精确定位、资产确认和链上资源追踪。基于这一特征，系统检索排序模块需要同时支持自然语言查询与链上身份查询，并在统一结果列表中给出清晰的排序依据。

本模块面向系统冷启动阶段的资源发现需求，设计目标包括以下四个方面。

\begin{enumerate}
    \item 当用户输入歌曲名、艺术家、专辑名或流派标签时，系统能够召回语义相关的链上音乐资源。
    \item 当用户输入Token ID、合约地址、交易哈希、IPFS CID或resourceKey等链上标识时，系统能够优先返回目标明确的资源。
    \item 当查询中存在大小写差异、空格变化、符号干扰或轻微拼写偏差时，系统仍能保持较好的召回能力与排序稳定性。
    \item 排序结果能够输出特征来源与得分原因，为结果分析、算法调试和用户侧解释提供依据。
\end{enumerate}

结合上述目标，本文将链上音乐资源检索排序模块划分为四个阶段：查询归一化、候选召回、特征评分和结果排序。该结构能够将查询处理、候选生成与排序决策解耦，便于后续扩展语义检索、行为反馈学习和在线权重优化等能力。

\section{检索对象与索引字段设计}

\subsection{检索对象定义}

系统以已发布的\texttt{CreatorRelease}作为检索对象。考虑到链上音乐资源需要具备可确认的链上身份，只有满足以下条件的资源才纳入检索范围：

\begin{enumerate}
    \item 资源状态为\texttt{PUBLISHED}；
    \item \texttt{chainId}非空；
    \item \texttt{musicAssetAddress}非空；
    \item \texttt{tokenId}非空。
\end{enumerate}

该约束保证了检索结果具备明确的链上可验证性，能够与后续播放、购买、确权和展示等业务环节形成一致的数据基础。

\section{查询处理与候选召回}

\subsection{查询归一化}

由于用户输入可能受到大小写、分隔符、拷贝格式以及轻微拼写偏差的影响，系统在召回前首先对原始查询进行归一化处理。归一化流程包括以下步骤：

\begin{enumerate}
    \item 对原始查询执行Unicode NFKC归一化，以统一全角半角字符和兼容字符表示；
    \item 将字母统一为小写形式；
    \item 合并多余空格并去除首尾空白；
    \item 按非字母数字分隔符切分词元；
    \item 生成用于紧凑比较的\texttt{compact}文本，以支持跨空格和符号差异的匹配。
\end{enumerate}

在归一化基础上，系统还会识别几类具有显著格式特征的链上输入，包括EVM地址、IPFS CID、Token ID、交易哈希和\texttt{resourceKey}。当查询被识别为此类字段时，排序阶段会显著提高身份字段的匹配优先级，以增强精确定位能力。

本文当前实现采用字符串归一化与轻量词元切分方案，尚未引入完整中文分词与向量语义检索模型。该设计与原型系统的冷启动背景相适配。一方面，资源规模较小，字符串匹配与编辑距离方法足以覆盖大部分典型查询；另一方面，固定规则方法具备良好的可复现性与解释性，便于算法分析与后续消融实验。

\subsection{候选召回策略}

候选召回采用“字段召回+近期补充”的两阶段策略。设用户查询为$q$，候选集合记为$C$。系统首先基于归一化后的查询执行数据库字段召回，获得候选集合$C_1$；随后引入一批近期发布资源作为补充集合$C_2$，并与$C_1$合并去重，得到最终候选集合$C$。

其中，$C_1$主要通过数据库中的\texttt{contains}条件构造，召回目标字段包括标题、艺术家、专辑、流派、描述以及链上身份字段。该阶段能够较高效地覆盖精确匹配、包含匹配和部分格式变化场景。

考虑到仅依赖SQL字段包含匹配时，轻微拼写误差和非标准输入可能导致漏召回，系统进一步引入近期发布资源作为模糊匹配补充集合$C_2$。该设计能够在候选范围内保留一定数量的新资源，为编辑距离相似度计算提供可比较对象。对于冷启动平台而言，近期资源同时具有更高的业务关注度，因此该补充策略在召回鲁棒性与系统资源开销之间取得了较好的平衡。

为控制评分阶段的计算复杂度，系统对候选规模设置上限。当前实现中，主召回候选数根据查询命中情况动态调整，总量限制在500条以内；补充召回的近期资源不超过200条。该限制能够保证排序阶段在常规负载下保持可控延迟。

\section{排序特征设计与评分模型}

\subsection{排序模型定义}

本文采用固定权重的多特征加和模型对候选资源进行排序，算法名称定义为\texttt{chain\_resource\_rank\_v1}。对任意候选资源$d$和查询$q$，其总分定义为

\begin{equation}
    Score(d,q)=S_{identity}(d,q)+S_{text}(d,q)+S_{fuzzy}(d,q)+S_{freshness}(d)+S_{popularity}(d)
    \label{eq:rank_score_rewrite}
\end{equation}

其中，$S_{identity}$表示身份匹配分，$S_{text}$表示文本匹配分，$S_{fuzzy}$表示模糊相似度分，$S_{freshness}$表示时效性分，$S_{popularity}$表示热度分。

该评分结构对应三类决策信息。第一类为资源定位信息，用于判断候选资源与查询在链上身份层面的对应关系；第二类为内容相关信息，用于判断候选资源与查询在标题、艺术家和专辑等语义层面的接近程度；第三类为辅助区分信息，用于在多个相关候选之间进一步比较新旧程度与受欢迎程度。整体结构如图\ref{fig:ranking_score_model}所示。

\subsection{身份匹配特征}

身份匹配特征面向链上资源的高确定性定位需求，覆盖\texttt{resourceKey}、\texttt{tokenId}、\texttt{musicAssetAddress}、\texttt{publishTxHash}以及各类CID字段。此类字段具有唯一性强、歧义度低、定位能力高的特点，因此在总分中赋予较高权重。

当前实现中，\texttt{resourceKey}、\texttt{tokenId}、音乐合约地址和IPFS CID的精确匹配权重分别设置为100、80、70和65。其权重设置依据主要来自字段的业务作用与定位强度：\texttt{resourceKey}直接对应系统内部资源标识，具有最高区分度；\texttt{tokenId}在指定合约上下文中具有明确唯一性；合约地址能够稳定定位到资源集合或资产发行主体；CID能够定位到链下内容对象，在链上音乐场景中同样具有较强的检索价值。

\subsection{文本匹配特征}

文本匹配特征覆盖标题、艺术家、专辑、流派和描述五类字段。系统分别考虑精确匹配、前缀匹配、包含匹配和词元重合四种信号，并通过加权方式体现不同字段与不同匹配关系的重要程度。

当前实现中的文本字段权重如下：

\begin{itemize}
    \item 标题字段的精确匹配、前缀匹配、包含匹配和词元重合权重分别为45、30、20和14；
    \item 艺术家字段分别为34、24、16和12；
    \item 专辑字段分别为24、16、10和8；
    \item 流派字段分别为20、14、8和6；
    \item 描述字段分别为10、8、6和4。
\end{itemize}

上述设置体现了查询意图在不同字段上的重要性差异。标题通常最直接反映用户的目标作品，因此具有最高权重；艺术家和专辑承担较强的检索引导作用，其次参与排序；流派更多服务于主题浏览和风格发现；描述字段文本长度较长、表述方式不稳定，其作用主要体现在辅助召回和弱相关区分。

\subsection{模糊相似度特征}

为增强系统对轻微拼写错误、分隔符变化和局部字符缺失的鲁棒性，排序阶段引入模糊相似度特征。本文采用基于Levenshtein距离的归一化字符串相似度，对查询与候选资源的\texttt{compact}文本进行比较。设归一化后的查询紧凑文本为$q_c$，候选字段紧凑文本为$d_c$，则相似度可表示为

\begin{equation}
    sim_{lev}(q_c,d_c)=1-\frac{Lev(q_c,d_c)}{\max(|q_c|,|d_c|)}
    \label{eq:lev_similarity}
\end{equation}

其中，$Lev(\cdot)$表示编辑距离，$|\cdot|$表示字符串长度。相似度越高，表示二者在字符层面越接近。

为降低短字符串导致的误召回风险，系统仅在\texttt{compact}文本长度不小于3时启用模糊相似度评分；当查询长度较短时，系统采用更高的相似度阈值。该约束能够抑制由极短词、缩写和单字符差异造成的不稳定排序现象。

\subsection{新鲜度与热度特征}

在多个候选资源都满足文本相关或身份相关条件时，系统进一步引入时效性与热度特征进行区分。

新鲜度分采用指数衰减形式。设资源发布时间距当前时刻的天数为$ageDays$，则新鲜度定义为

\begin{equation}
    freshness(d)=0.5^{ageDays/45}
    \label{eq:freshness_rewrite}
\end{equation}

该式表示资源每经过45天，其新鲜度贡献衰减为原值的一半。当前实现中，新鲜度项的最高贡献为8分。该设计能够使近期发布资源在分值接近时获得更高排序位置，同时避免时间因素过度主导结果顺序。

热度分由评论数与购买数共同决定，其归一化形式为

\begin{equation}
    popularity(d)=\min\left(1,\frac{\ln(1+comments+3\times purchases)}{\ln(31)}\right)
    \label{eq:popularity_rewrite}
\end{equation}

当前实现中，热度项的最高贡献为7分。式中对购买数给予更高权重，原因在于购买行为代表了更强的资源确认信号与价值投入，相较评论行为具有更高的可信度和业务指向性。对数归一化处理能够减弱极端高活跃样本对排序结果的影响，使热度特征在不同规模资源之间保持更平滑的区分能力。

\section{排序解释机制与算法流程}

\subsection{排序解释机制}

为了增强检索结果的可分析性，系统在输出排序结果时同步记录各项得分来源。对于每个候选资源，系统保留以下解释信息：

\begin{enumerate}
    \item 命中的字段类型，如标题、艺术家、Token ID或CID；
    \item 命中的匹配关系，如精确匹配、前缀匹配、包含匹配、词元重合或模糊相似；
    \item 各项特征分值及其对总分的贡献；
    \item 新鲜度与热度的归一化得分。
\end{enumerate}

例如，当某一资源因标题精确匹配获得45分、艺术家前缀匹配获得24分、新鲜度获得6.3分、热度获得4.8分时，系统能够在结果明细中展示上述组成，从而使排序结论具备可追踪性。该机制有助于分析误召回、定位参数设置问题，并为后续算法优化提供依据。

\begin{breakablealgorithm}
    \caption{链上音乐资源检索与排序算法}
    \label{algo:chain_resource_rank_rewrite}
    \begin{algorithmic}[1]
    \Require 用户查询$q$，返回数量$k$
    \Ensure 排序后的链上音乐资源列表
    \State 对$q$进行归一化处理，得到词元集合、\texttt{compact}文本和特殊链上字段识别结果
    \State 基于标题、艺术家、专辑、流派、描述及链上身份字段执行数据库召回，得到候选集合$C_1$
    \State 选取近期发布资源构成补充集合$C_2$
    \State 合并并去重，得到最终候选集合$C=C_1\cup C_2$
    \For{每个候选资源$d \in C$}
        \State 计算身份匹配分$S_{identity}(d,q)$
        \State 计算文本匹配分$S_{text}(d,q)$
        \State 计算模糊相似度分$S_{fuzzy}(d,q)$
        \State 计算新鲜度分$S_{freshness}(d)$
        \State 计算热度分$S_{popularity}(d)$
        \State 汇总总分$Score(d,q)$并记录排序解释信息
    \EndFor
    \State 过滤未命中有效相关特征的候选资源
    \State 按总分降序排序；若总分相同，则按发布时间降序排序
    \State 返回前$k$个结果
    \end{algorithmic}
\end{breakablealgorithm}

\section{复杂度分析}

设候选资源数量为$N$，平均参与比较的文本长度为$L$。候选召回阶段主要由数据库字段查询完成，计算开销主要集中在排序阶段。

文本匹配分的计算主要依赖字段比较与词元重合统计，其时间复杂度近似为$O(NL)$。模糊相似度采用Levenshtein距离，在单次比较中的时间复杂度近似为$O(L^2)$，因此在候选集合上的总体复杂度近似为$O(NL^2)$。最终排序采用基于总分的比较排序，其复杂度为$O(N\log N)$。

考虑到编辑距离计算对长文本较为敏感，系统在实现中对参与模糊比较的文本长度进行截断，并对候选数量设置上限，因此整体运行开销能够维持在可接受范围内。对于原型系统当前的资源规模，该复杂度设计能够满足离线评估与在线检索的基本需求。

\section{检索效果评估设计}

为验证检索排序模块在冷启动阶段的有效性，本文构建了一个离线评估集。该评估集包含56条模拟链上音乐资源和62个查询，按照14个艺术家或专辑簇组织，用于覆盖多种具有代表性的检索情形。

在查询类型方面，评估集包括中英文标题检索、长专辑名检索、流派检索，以及Token ID、合约地址、IPFS CID、\texttt{resourceKey}和交易哈希等链上身份检索。该设计能够同时考察系统对自然语言查询和链上标识查询的处理能力。

在相关性标注方面，单目标定位类查询采用唯一三级相关资源标注方式，适用于标题、Token ID、CID和\texttt{resourceKey}等高确定性场景；艺术家、专辑和流派等多结果查询采用三级相关性标注，按照查询意图匹配程度和资源代表性标记为3、2、1三个等级。该标注方式能够更细致地反映多结果场景下的排序优劣。

需要说明的是，当前评估集属于面向原型验证的结构化模拟数据集，主要用于检验冷启动阶段检索链路的工程可用性与排序合理性。基于真实线上行为日志构建的大规模评估体系仍需在系统投入实际运行后进一步完善。

本文采用以下指标评估检索效果：

\begin{enumerate}
    \item \textbf{Precision@10}：衡量前10个结果中的相关资源比例；
    \item \textbf{MRR}：衡量首个高相关结果出现的位置；
    \item \textbf{nDCG@10}：衡量前10个结果在分级相关性条件下的排序质量；
    \item \textbf{零结果率}：衡量检索请求中无返回结果的比例；
    \item \textbf{平均响应时间}：衡量检索链路的效率表现。
\end{enumerate}

对比方法设置为四组：数据库字段包含匹配基线、仅使用文本评分的方法、文本评分叠加链上身份字段的方法，以及完整的\texttt{chain\_resource\_rank\_v1}算法。通过分层对比，可以观察身份字段特征、模糊相似度特征以及辅助排序特征对整体检索效果的贡献。具体实验过程、数据分布和结果分析见第7章表\ref{tab:ranking_query_categories}、表\ref{tab:ranking_metrics_actual}和图\ref{fig:ranking_latency_curve}。

\section{本章小结}

本章围绕链上音乐资源检索排序模块的设计展开论述，完成了检索对象定义、索引字段划分、查询归一化方法、候选召回策略、排序特征构建、评分模型设计、解释机制建立以及评估方案设计。本文所提出的\texttt{chain\_resource\_rank\_v1}模型面向冷启动阶段的链上音乐平台，能够在缺乏大规模行为数据的条件下兼顾文本检索能力、链上身份定位能力与结果可解释性，为后续章节中的实验验证提供方法基础。
