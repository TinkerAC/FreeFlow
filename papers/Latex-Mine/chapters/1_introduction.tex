\chapter{绪论}

\section{研究背景与意义}

随着Spotify、Apple Music等中心化流媒体平台的发展，数字音乐作品的传播效率和消费便利性得到显著提升，音乐产业的生产、分发与消费模式也由此发生了深刻变化。然而，在平台化效率不断提高的同时，数字音乐领域长期存在的若干结构性问题并未得到根本解决，主要体现在版权确权可信度不足、授权链条复杂、收益分配透明性有限以及平台内外数据难以协同等方面。尤其对于独立音乐人和小型创作团队而言，作品发行、授权管理、收益核验和粉丝运营往往仍然高度依赖中心化平台及其中介机构，创作者对作品实际传播路径和收益流向的可见性较弱，版权凭证也较难在平台之外实现统一验证。

从技术角度看，区块链为数字音乐版权管理提供了一种新的可信记录机制。其不可篡改、可追溯和可编程的特性，使其适合用于记录作品登记、授权状态、交易过程和收益规则等高可信需求场景。与此同时，IPFS采用内容寻址方式保存文件，能够以内容哈希作为资源标识，为音频、封面、歌词、元数据等多媒体资源提供分布式存储支撑，从而形成“链上记录可信状态、链下保存内容资源”的分层架构。进一步地，基于标准消息签名的身份认证机制，如SIWE（Sign-In with Ethereum），能够以较低门槛实现Web3身份登录，将链上身份与链下会话管理结合起来，降低区块链系统的使用复杂度。

不过，现有研究和产业实践也表明，数字音乐领域的关键瓶颈并不只是“是否上链”。区块链可以改善可信留痕与规则自动执行问题，但无法单独替代版权法、行业标准、平台治理与现实合同关系。音乐产业中的真实难点仍然包括元数据质量不高、权利链条复杂、版税分配执行受限、跨平台数据协同困难，以及系统在成本、吞吐、维护性和法律效力之间的平衡问题。因此，数字音乐系统的设计重点不应停留于“强去中心化”的概念宣示，而应更关注链上确权与授权、链下索引与社区服务、去中心化文件存储与行业标准兼容之间的工程可行性。

基于上述背景，本文围绕FreeFlow项目，设计并实现一个基于区块链与IPFS的链上音乐发行与播放系统。系统面向创作者、普通用户和平台管理方，采用“桌面端/前端 + Web2.5后端 + 智能合约 + IPFS存储”的混合架构，在链上实现作品发布、访问授权、交易记录和收益规则管理，在链下实现资源索引、评论互动、搜索排序和内容服务，从而形成一个覆盖音乐发布、授权访问、社区互动和资源发现的完整业务闭环。

与仅关注版权存证或NFT收藏的平台不同，FreeFlow更强调面向实际使用流程的系统整合能力。一方面，系统以ERC-1155为核心资产标准，将音乐访问凭证、收听许可、会员资格或批量授权对象纳入统一合约模型，提升同一平台内多类数字权益表达的灵活性和工程效率；另一方面，系统不将全部内容与索引直接上链，而是采用链上状态与链下服务协同的方式，在保证可信记录的同时兼顾访问效率与部署成本。与此同时，系统还引入链上音乐资源检索与排序模块，以适应平台冷启动阶段用户行为数据不足的特点，通过可解释的特征设计提升资源发现能力。

因此，本文研究的意义主要体现在以下几个方面：第一，从数字音乐系统设计视角出发，探索区块链、IPFS与桌面端播放系统的协同方式，为链上音乐发行与消费提供一种可运行的实现路径；第二，从平台架构角度验证“链上高可信记录 + 链下内容索引与社区服务”的混合模式在数字音乐场景中的适用性；第三，在技术选型层面明确ERC-1155、SIWE、IPFS与Web2.5后端之间的职责边界，为后续扩展到收益分账、内容治理和跨平台互操作提供基础；第四，通过引入资源检索与排序模块，将音乐版权管理、用户访问控制和音乐资源发现纳入统一系统框架，增强平台的实际使用价值。

\section{国内外研究现状}

\subsection{数字音乐发行系统研究现状}

现有数字音乐平台大多采用中心化架构完成作品上传、分发、访问控制和收益结算，其优势在于系统成熟、服务稳定和用户规模庞大，但也带来了创作者对平台依赖度高、作品流转记录难以独立验证、收益链条不透明等问题。围绕数字音乐发行与版权管理，相关研究主要集中在数字版权管理、流媒体平台治理、创作者经济和音乐产业价值链重构等方向。

从产业问题研究看，已有文献较充分揭示了数字音乐领域的核心矛盾。相关研究指出，作品、录音、表演者、出版者和权利份额等信息通常分散在不同数据库中，导致元数据缺失、标识不一致和权利链条断裂等问题。与此同时，版权授权、收益报送和版税清分过程又往往依赖多层中介机构，使创作者难以及时核验作品传播情况与实际收益。研究还表明，在流媒体内容规模快速增长的背景下，元数据不一致、许可结构复杂和版税发放效率低下，已成为数字音乐产业中最具代表性的结构性障碍。

与国外偏重开放生态和协议创新的研究路径相比，国内关于数字版权与区块链的实践更强调版权存证、侵权监测、司法协同和版权服务平台建设。此类研究通常将区块链视为数字版权基础设施的一部分，重点在于通过链上存证、取证、发函、调解和诉讼支撑等环节提升版权保护效率，而非简单构建完全去中介化的流媒体平台。这也说明，在中国语境下，数字音乐系统若引入区块链，往往需要兼顾工程实现与治理衔接，而不能仅强调技术替代。

总体而言，现有数字音乐发行系统研究在平台功能、流媒体服务和版权管理方面已形成较多成果，但对于“发布—授权—访问—互动—发现”全流程一体化设计的关注仍然有限。特别是在创作者自主发行、链上访问控制、用户社区互动和音乐资源检索协同方面，仍缺乏一个兼顾工程可行性与系统完整性的实现框架。

\subsection{区块链与IPFS在数字内容管理中的应用}

区块链与IPFS已成为数字内容管理领域的重要技术组合。区块链通过共享账本和智能合约实现数字资产状态记录、规则执行与交易留痕，适合承载作品登记、访问授权、交易记录和收益规则等高可信业务。IPFS则以内容寻址机制为核心，通过CID将文件内容与唯一哈希对应起来，适合保存音频、封面、歌词、元数据以及相关证据材料，为链上状态提供链下内容支撑。

在区块链数字内容管理研究中，已有工作大致可分为四类。第一类是问题诊断与制度分析型研究，主要关注音乐行业中元数据、授权链条和版税体系的现实困境，为后续技术方案设计提供问题基础。第二类是版权存证与交易系统型研究，通常基于Ethereum、Hyperledger Fabric等平台实现音乐版权登记、交易流转、分账或侵权取证，是最接近系统实现路径的一类研究。第三类是激励与收益分配型研究，重点探索公有链环境下通过代币激励、奖励惩罚和社区投票等机制抑制非法传播并提升内容流通效率。第四类是协议和社区经济型研究，强调艺术家与粉丝之间的直接价值连接、开放目录和音乐NFT标准化，反映出音乐Web3系统正在从单一平台实验逐步向协议和生态协同演进。

在资产标准方面，ERC-721适合表达唯一且可区分的数字凭证，而ERC-1155则更适合同一合约下同时表达多种可替代或不可替代资产，尤其适用于访问票据、会员资格、批量授权和多类型权益并存的业务场景。对于链上音乐发行系统而言，音乐作品本身的权利归属、访问资格和社区权益并不一定适合用同一种资产范式表达；若平台更强调访问控制、购买许可和批量发放能力，ERC-1155通常较ERC-721更具工程效率和实现弹性。因此，本文系统采用ERC-1155作为核心链上凭证标准，以支持音乐访问授权与平台内数字权益管理。

在身份与版税标准层面，SIWE能够通过签署标准消息完成身份登录，不需要用户为登录动作支付链上手续费，有助于改善Web3系统用户体验。EIP-2981则为版税信息读取提供了统一接口，但其本质上只定义“如何读取版税信息”，并不强制交易平台实际付款，因此“版税可编程”并不等同于“版税必然执行”。这一点也说明，区块链系统能够增强规则表达与自动执行能力，但对于版税结算和权利执行，仍然需要平台治理和外部制度环境配合。

在部署与架构层面，越来越多研究采用“链上可信状态 + 链下服务协同”的混合模式，而不是把音频文件、评论数据或全文检索数据直接存储到区块链主网上。这种架构一方面利用区块链提供可信记录与授权状态，另一方面通过数据库、后端索引和IPFS提升系统吞吐、访问性能和维护性，已逐步成为数字内容管理系统的主流工程路线。由此可见，区块链和IPFS的结合并非为了彻底替代现有平台基础设施，而是为了在可信留痕、授权管理和内容分发之间形成更合理的职责分层。

\subsection{音乐检索与资源排序研究现状}

音乐检索与资源排序是数字音乐平台中的关键组成部分，其目标在于帮助用户从海量音乐资源中高效发现感兴趣的内容。传统音乐检索通常包括基于标题、艺人、专辑、标签和描述文本的元数据检索，也包括基于音频内容特征的相似度检索、推荐系统和个性化排序等方向。在成熟平台中，检索和推荐往往能够结合用户行为数据、内容特征和上下文信息共同优化排序效果；但对于冷启动阶段的平台而言，用户行为数据通常有限，复杂的个性化模型难以充分发挥作用，此时基于可解释特征的检索排序方法仍具有较高的实用价值。

从研究积累来看，音乐信息检索领域已经形成较成熟的数据集与评价指标体系。Million Song Dataset、FMA和LFM-1b等数据集分别从大规模音频特征、开放音乐元数据和听歌行为事件等方面为音乐检索、召回和推荐研究提供支撑；而MusDB18等数据集则更适合音频分离、水印检测和音频处理任务。这说明，“音乐平台系统研究”与“音乐算法评测”在数据和任务上具有明显差异：前者更强调系统流程和功能闭环，后者更强调检索、推荐或音频分析算法的评价设计。因此，若系统包含独立的资源检索与排序模块，就有必要借鉴信息检索领域较成熟的评价方法，而不能仅以系统功能完成作为唯一依据。

在评价指标方面，检索和排序研究通常采用Precision@K、Recall@K、MAP、MRR和NDCG等指标衡量结果相关性和排序质量。近年来的研究还指出，若仅依赖离线精度指标，可能会高估系统对“已知艺人”和“热门作品”的偏好，而低估其帮助用户发现新艺人、新作品的能力。因此，在音乐资源冷启动场景下，除了基本的相关性指标，还应关注覆盖率、多样性和公平性等维度，避免资源排序被简单地退化为对热门资源的重复放大。

结合FreeFlow项目的实际情况，平台当前处于链上音乐资源的冷启动阶段，尚未积累大规模稳定的用户行为数据，因此本文在检索与排序模块中更适合采用可解释特征模型。具体而言，可综合标题、艺人名、描述文本、标签字段、链上身份字段、新鲜度信号与热度信号等因素构建排序公式，在保证实现复杂度可控的前提下提升系统资源发现能力。这种设计既符合系统当前发展阶段，也有助于后续平滑扩展至更复杂的推荐模型。

综合来看，现有研究在数字音乐平台、区块链内容管理和音乐资源检索三个方向上均已形成一定积累，但三者之间仍存在明显割裂：数字音乐平台研究更多聚焦业务模式与版权体系，区块链研究更关注确权、交易和智能合约，音乐检索研究则偏重算法效果与数据集评测。如何将链上发布、访问控制、用户互动与资源发现有机结合，并在系统层面实现闭环，仍然是当前研究中的一个值得继续深入的问题。

\section{研究内容与主要工作}

本文围绕FreeFlow链上音乐发行与播放系统展开研究，目标是构建一个融合区块链、IPFS、身份认证、音乐资源索引与用户互动的完整平台，实现从创作者发布到用户消费的业务闭环，并验证该类混合架构在可信记录、低成本部署、访问控制和资源发现方面的可行性。本文的主要工作包括以下几个方面：

\begin{enumerate}
    \item 设计FreeFlow链上音乐发行与播放系统的总体架构，明确桌面端、Web2.5后端、智能合约和IPFS存储之间的职责边界，构建“链上状态可信、链下服务高效”的混合系统方案。

    \item 设计并实现创作者工作台，支持作品草稿管理、音乐信息编辑、素材上传、metadata生成、IPFS资源存储、链上发布以及发行状态查询等功能，使创作者能够完成从内容准备到上链发布的完整流程。

    \item 设计并实现Web2.5后端服务，提供SIWE登录、Pinata上传代理、发行状态管理、链上资源索引、购买记录、评论管理和用户资料维护等能力，实现链上业务流程与链下应用服务之间的协同。

    \item 设计并实现智能合约模块，以ERC-1155作为核心资产标准，完成音乐访问凭证的铸造、购买授权、权限校验和平台内数字权益表达，并结合发布合约与收益规则设计实现链上发行与授权控制逻辑。

    \item 设计并实现链上音乐资源检索与排序模块，围绕标题、艺人、描述、标签、链上身份字段、新鲜度和热度信号构建资源发现机制，以适应平台冷启动阶段用户行为数据不足的特点，提升资源搜索与排序效果。

    \item 设计并实现桌面端用户侧功能，包括链上音乐库、播放器、音频代理、Range请求支持、评论互动、下载管理和访问校验等能力，增强用户在音乐收听、缓存和系统级交互方面的体验。

    \item 从系统功能、接口交互、合约调用、资源访问稳定性、检索排序效果和性能开销等多个维度开展测试与分析，评估系统在可用性、透明性、成本和扩展性方面的整体表现。
\end{enumerate}

总体而言，本文并不试图将区块链视为对现实音乐产业的全面替代方案，而是将其作为可信记录与授权执行机制嵌入数字音乐平台架构之中。系统的重点在于验证：在链上确权与访问控制、链下索引与社区服务、去中心化文件存储和标准化身份认证之间，是否能够形成一个工程上可实现、流程上可闭环、使用上可接受的音乐应用系统。

\section{论文组织结构}

本文共分为八章，各章安排如下。

第一章为绪论，介绍数字音乐平台和链上内容管理的发展背景，分析国内外研究现状，阐明本文的研究内容、主要工作及论文整体结构。

第二章介绍系统实现所依赖的关键技术，包括区块链与智能合约、ERC-1155数字资产标准、SIWE身份认证、IPFS内容寻址存储、Web2.5后端架构以及音乐资源检索与排序的基本方法。

第三章进行系统需求分析，从创作者、普通用户与平台管理者三个角色出发，分析平台在作品发布、访问授权、交易记录、评论互动、搜索发现和系统安全等方面的功能需求与非功能需求。

第四章给出系统总体设计，重点说明系统总体架构、模块划分、核心业务流程、数据库与索引设计、智能合约设计以及链上链下协同的安全边界。

第五章介绍系统核心模块实现，包括SIWE登录、用户资料管理、创作者工作台、素材上传、IPFS存储、链上发布、购买验证、播放器和评论模块等关键功能的实现方式。

第六章介绍链上音乐资源检索与排序模块，说明索引字段设计、查询归一化、候选召回、特征构建、排序公式与评估方法，并结合平台冷启动场景分析该策略的适用性。

第七章进行系统测试与效果分析，从功能正确性、接口调用、合约交互、性能开销、资源访问稳定性与检索效果等方面评估系统整体表现。
