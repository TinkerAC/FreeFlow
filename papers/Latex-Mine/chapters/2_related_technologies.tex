\chapter{相关技术}

本章围绕FreeFlow系统实现所依赖的关键技术展开说明。结合链上音乐发行、访问控制、资源存储与桌面端播放等业务需求，系统采用桌面端应用、链下服务、智能合约与内容寻址存储协同的技术方案。以下从应用架构、身份认证、资源存储、链上合约与播放支撑五个方面介绍相关技术基础。

\section{桌面端与链下服务技术基础}

FreeFlow 选用 Electron 与 React 来构建桌面端，同时还采用了 Node.js、Express 以及 Prisma 来搭建链下服务。这套技术组合能够去处理桌面应用交互、本地能力调用、HTTP 接口组织以及关系型数据管理等方面的核心需求的相关工作。

Electron 提供了跨平台桌面应用的运行环境，同时还依靠主进程与渲染进程的分工来承载系统功能\cite{electronDocs,electronIPC}。在本系统当中，主进程会负责窗口管理、本地数据库访问、下载与缓存控制、音频代理等本地能力方面的管理工作；渲染进程则会去开展创作者工作台、资源检索、详情展示、评论与播放控制等界面交互方面的工作。

React 被运用于组织前端组件与状态流，这样一来，播放器、作品列表、评论区与发行工作台等界面模块便具备了较好的可维护性\cite{reactDocs}。

链下服务是依靠 Node.js 与 Express 来构建的。Node.js 比较适宜去处理上传、流式转发以及链上交互代理等 I/O 密集型任务，而 Express 则便于去组织认证、资源、购买、评论以及异常处理等业务接口\cite{nodeDocs,expressDocs}。在数据持久化这个方面，系统运用了 PostgreSQL 来保存用户、钱包身份、发行记录、上传记录、购买记录与评论数据，并且凭借 Prisma 来完成模式定义、关系映射以及迁移管理工作\cite{prismaDocs}。该技术组合为后续的资源索引、分页查询、业务状态维护以及系统联动提供了比较稳定的数据支撑。

\section{SIWE身份认证机制}

系统身份认证选用了 SIWE（也就是 Sign-In with Ethereum）方案，它的消息格式是由 EIP-4361 来定义的\cite{eip4361}。该机制凭借钱包签名来证明用户对链上地址的控制权，能够把系统身份与链上账户建立起统一的关联关系，方便后续的购买、发布以及访问校验等流程去复用同一个身份基础。

在具体实现当中，后端会先生成一个一次性的随机数 nonce，并且构造出包含域名、地址、URI、链 ID、签发时间等字段的标准化消息；客户端调起钱包完成签名之后，再把签名结果和原始消息一起提交给后端；后端随后会对消息格式、nonce 有效性、链 ID 以及签名恢复地址进行校验\cite{eip4361}。一旦验证通过，系统就会去创建或绑定用户实体、钱包身份以及会话记录，并把后续的业务操作统一关联到这个地址身份上来。

相比传统的账户口令体系，SIWE 降低了独立密码存储与找回流程所带来的维护方面的负担，与此同时，它还增强了桌面端身份体系与链上访问控制之间的一致性，因此比较契合本系统的应用场景。

\section{IPFS内容寻址存储与混合架构}

链上音乐系统牵涉到媒体资源的存储、可验证的引用以及高频的业务协同。正是鉴于这一特性，FreeFlow 把区块链、IPFS 以及链下服务组合成了混合架构，以便去兼顾可信记录、资源可定位性还有系统运行效率。

IPFS 运用了内容寻址机制，用 CID 来标识文件内容。当资源内容发生变化的时候，它所对应的 CID 也会跟着变化，因此比较适宜去发布和引用音频文件、封面图以及 metadata 等静态对象\cite{ipfsDocs}。本系统采用了 Pinata 来完成上传与持久化的管理工作，在创作者发布的流程当中会去保存音频、封面和 metadata 对象，并且获得对应的 CID 或网关地址\cite{pinataDocs}。考虑到 IPFS 本身主要负责寻址与分发方面的工作，资源的长期可用性还是要依赖于持续的保存机制，系统便凭借 Pinata 的持久化服务来降低节点维护以及 pinning 管理方面的复杂度\cite{ipfsPinning}。

在系统层面，作品发布结果、访问凭证、交易记录以及收益规则等关键状态会被保存到链上；而评论、资源索引、登录会话、上传状态与检索支撑数据则保存于链下。已经有研究指出，链上、链下以及混合模式在成本、吞吐、可扩展性还有可信性之间存在着明确的权衡关系，面向实际应用的区块链系统通常需要把链上记录与链下处理结合起来去开展协同设计\cite{Wei2022BDMSSurvey,Six2022DAppPatterns,Liu2020GasExceptions}。对于音乐场景来说，媒体文件的体积是比较大的，评论与检索数据的更新也比较频繁，如果全部依靠链上处理，那就会明显增加存储与交互的成本；把高可信状态和高频服务进行分层组织，会更加契合系统当前的规模与实现目标。

\section{智能合约与ERC-1155访问凭证}

链上业务逻辑选用了 Solidity 来进行实现\cite{solidityDocs}。系统围绕作品发布、访问授权以及收益分配这几个方面来设计合约结构，其中的访问控制是以 ERC-1155 多代币标准作为基础的\cite{eip1155}。

ERC-1155 允许在同一份合约里面去管理多种代币类型，比较适宜把每首作品映射成独立的\texttt{tokenId}访问凭证。在 FreeFlow 当中，用户完成购买以后会获得对应的\texttt{tokenId}，系统就据此去开展访问状态的校验工作。由于这个凭证在业务语义上所承载的是作品的访问资格，在合约实现当中需要对普通的转移行为施加限制，以此来维持访问控制与购买关系之间的一致性。

系统的合约主要包括了 \texttt{MusicAccess1155}、\texttt{PlatformHub} 以及 \texttt{RoyaltySplitter}。\texttt{MusicAccess1155} 负责访问凭证的创建与校验工作；\texttt{PlatformHub} 负责作品发布、销售参数维护、购买处理以及访问判断方面的工作；\texttt{RoyaltySplitter} 则负责收益的分账与提取操作。凭借上述合约之间的协作，系统可以完成作品发布、凭证发放以及收益流转等核心链上业务。为了提升标准实现的可靠性，开发过程当中复用了 OpenZeppelin 所提供的一系列合约组件与安全工具库\cite{openzeppelinContracts}。

\section{音频代理、Range请求与本地缓存}

在线播放场景对于随机访问、进度跳转以及重复播放效率这几个方面有着比较高的要求。为了提高桌面端的播放稳定性，系统在本地集成了音频代理服务，同时把本地文件、缓存文件以及远程音频统一都纳入到同一个访问入口里面。

播放器会通过本地代理接口来请求音频数据，而代理层则会根据资源状态去判断是直接读取本地文件、还是返回缓存内容，又或者是向远程地址发起转发请求。这种方式便于集中地去处理资源定位、缓存命中、错误恢复还有播放链路控制方面的工作。对于拖动进度条、断点续播等操作来说，系统依赖 HTTP Range 机制去完成按字节区间的读取工作。依据 HTTP 语义规范，客户端可以凭借\texttt{Range}请求头来指定所要获取的区间，服务端在支持的情况下会返回\texttt{206 Partial Content}响应\cite{rfc9110}。这种机制有助于降低重新加载完整音频文件所带来的时间方面的开销。

在实现这个层面上，Node.js 所提供的 HTTP 与流式处理方面的能力比较适宜音频转发和缓存写入这类场景\cite{nodeHttp,nodeStream}。系统针对普通的播放请求会采用边传输边缓存的策略，而对于范围请求则会优先去透传上游的分段响应，这样一来，就能在保证跳转实时性的同时，也兼顾到后续的复用效率。这样的设计为链上音乐的播放、试听还有下载管理提供了必要的桌面端支撑。
