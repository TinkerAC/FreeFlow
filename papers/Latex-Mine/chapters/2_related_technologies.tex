\chapter{相关技术}


\section{Electron与React桌面端开发}

FreeFlow桌面端采用Electron与React构建。Electron本质上是一个基于Chromium与Node.js的跨平台桌面应用框架，其运行架构遵循主进程（Main Process）与渲染进程（Renderer Process）分离的进程模型。主进程负责应用生命周期管理、原生窗口创建、系统级能力调度以及与操作系统资源的交互；渲染进程负责承载具体页面，并以Web技术实现桌面端用户界面\cite{electronDocs,electronIPC}。在本系统中，主进程主要负责窗口管理、本地数据库访问、音频代理服务、本地文件下载与缓存管理，以及对外提供安全受控的进程间通信接口；渲染进程则负责主播放界面、设置界面、用户资料引导界面、创作者工作台、链上音乐详情页和评论页等前端交互功能。

React用于实现桌面端界面的组件化开发。React将界面抽象为可复用的组件，并通过状态（state）和属性（props）组织数据流，从而提高复杂交互界面的可维护性与可扩展性\cite{reactDocs}。FreeFlow将播放器、作品列表、评论区、创作者工作台、购买弹窗与系统设置等拆分为独立组件，使界面逻辑与业务逻辑能够分层组织，便于后续迭代。对于播放状态、用户登录状态、作品详情和访问权限等跨组件共享的数据，系统采用“状态上移”和统一状态管理的方式，减少重复状态带来的数据不一致问题。综合而言，Electron提供了桌面端宿主环境，React提供了高效的前端组件化开发能力，两者结合使系统能够同时具备桌面应用的本地能力与现代Web界面的开发效率。


\section{Node.js、Express与Prisma后端开发}

系统后端采用Node.js与Express构建HTTP API服务，并使用Prisma作为ORM框架连接PostgreSQL数据库。Node.js提供事件驱动、非阻塞I/O的服务端运行环境，适合实现文件上传、音频转发、链上交互代理等I/O密集型业务\cite{nodeDocs}。Express在Node.js之上提供轻量而灵活的Web应用开发能力，其核心机制包括路由、中间件链与请求/响应处理接口，便于将认证、上传、评论、购买和异常处理等功能按模块组织\cite{expressDocs}。

Prisma为系统提供类型安全（type-safe）的数据访问能力，并以声明式模式（schema）描述数据库模型、字段约束及表间关系\cite{prismaDocs}。本系统使用PostgreSQL保存用户、钱包身份、上传记录、创作者发行记录、购买记录、评论与系统配置等数据。结合Prisma后，后端能够以统一的数据抽象完成增删改查操作，并通过迁移机制维护数据库结构演进。

在数据建模方面，创作者发行表是系统的核心业务表之一。该表主要保存作品标题、作者信息、封面与音频的IPFS资源引用、metadata URI、合约地址、tokenId、发布交易哈希、销售参数、访问模式和发布状态等信息。由于链上数据更适合记录关键状态与可验证凭证，而复杂检索与分页展示更依赖关系型数据库，因此系统将“链上可信状态”与“链下业务索引”相结合：区块链用于保存作品发行结果、购买凭证与收益分配规则，PostgreSQL用于支持作品检索、用户中心展示、后台管理与评论查询等高频业务场景。


\section{SIWE钱包登录机制}

SIWE（Sign-In with Ethereum）是一种基于以太坊账户签名的身份认证方案，其消息格式由EIP-4361标准定义\cite{eip4361}。用户通过钱包对标准化文本消息进行签名，以证明其对某个链上地址的控制权，同时避免额外维护独立口令体系。

本系统中，后端首先生成一次性随机数nonce，并构造符合EIP-4361格式的登录消息。该消息通常包含域名（domain）、钱包地址（address）、URI、协议版本、链ID、nonce、签发时间（issued at）等字段，必要时还可包含过期时间、声明信息和请求资源等扩展字段\cite{eip4361}。桌面端调起用户钱包完成签名后，将签名结果与原始消息提交至后端。后端对消息格式、nonce是否匹配、消息是否超时、链ID是否符合系统要求以及签名恢复得到的地址是否与声明地址一致进行校验。校验通过后，系统创建或绑定用户实体、钱包身份记录与会话信息，并将后续购买、发行、评论等行为统一关联到该钱包身份之下。

采用SIWE机制有两方面优势。其一，系统身份与链上地址天然绑定，能够直接复用于后续链上购买、访问权验证与创作者身份确认。其二，该方案避免了传统密码存储与找回流程所带来的额外安全负担，更契合Web3应用中“用户以钱包为身份入口”的交互习惯。


\section{IPFS与Pinata内容寻址存储}

IPFS（InterPlanetary File System）是一组面向内容寻址、路由与数据传输的开放协议。与传统基于位置的URL寻址不同，IPFS使用内容标识符CID（Content Identifier）来唯一标识内容；当文件内容发生变化时，其对应CID也会随之变化\cite{ipfsDocs}。这种内容寻址机制有助于保证资源引用的稳定性与可验证性，因此适合用于音频文件、封面图以及metadata JSON等静态数字内容的发布与分发。

本系统采用Pinata作为IPFS上传与持久化服务。创作者上传作品时，系统将音频文件、封面文件以及描述作品名称、作者、封面链接、音频链接等信息的metadata JSON上传至Pinata，并获取对应CID或可访问的网关地址\cite{pinataDocs}。需要指出的是，IPFS本身侧重内容寻址与分发，数据是否能够长期可用还依赖于至少一个节点持续保存该内容；因此，为保证资源不因垃圾回收而失效，通常需要借助pinning机制或第三方持久化服务进行保留\cite{ipfsPinning}。本系统选择Pinata，正是为了降低自行维护IPFS节点与持久化策略的复杂度。

在链上发布阶段，系统将作品metadata URI写入智能合约关联的资源字段中。这样，链上记录保存的是对资源的可验证引用，避免把大体积媒体文件直接写入链上。该设计既控制了音频上链带来的极高存储成本，也保留了作品资源可追溯、可校验与可跨平台解析的能力。因此，IPFS主要承担数字资源的存储与分发职责，区块链则承担访问凭证、交易记录与收益规则的可信记账职责，二者共同构成链上音乐系统的数据基础设施。


\section{Web2.5协同架构与治理边界}

在Web3语境中，“去中心化平台”往往不仅意味着数据上链或资产代币化，还意味着治理代币、提案机制、投票流程、激励约束以及内容治理规则等一整套组织机制的设计与运行。相关研究指出，平台治理效果取决于成本、效率、协调难度和参与门槛等因素，复杂业务通常需要在中心化、半去中心化与去中心化之间进行权衡\cite{Chen2021,Rikken2019}。对于DAO类组织而言，提案管理、投票结构、代币分配和治理参与度本身就是独立而复杂的研究议题\cite{Alawadi2024}。

对音乐平台而言，这种复杂性还会进一步叠加内容审核、侵权争议、社区秩序维护和多方协作创作等问题。音乐平台始终需要处理内容治理问题，治理权力如何分配、争议如何处理以及审核责任如何落地，都会直接影响平台可运行性\cite{Friedl2024}。与此同时，评论、全文检索索引、登录会话、上传状态等数据具有高频写入、快速查询和需要运维调整的特点，若完全上链，不仅会持续消耗gas，还会受到区块确认延迟、链上吞吐和数据不可逆更新的约束，不利于音乐应用中的即时互动与内容服务。

与此同时，链上、链下与混合存储方案在安全性、成本和可扩展性上存在明确权衡。相关综述表明，完全链上存储虽然具有较高的不可篡改性，但会带来显著的存储成本和吞吐压力；纯链下模式则更易扩展，但需要额外机制保证资源引用和访问控制的可信性；混合模式因此成为兼顾安全、成本和性能的常见工程方案\cite{Eren2025}。基于上述原因，FreeFlow采用Web2.5协同架构：将作品发布、访问凭证、交易记录等高可信状态放在链上，将认证会话、资源索引、评论和上传代理等高频服务放在链下，以兼顾治理复杂度、交互响应速度与系统维护成本。


\section{Solidity智能合约与ERC-1155访问凭证}

智能合约部分采用Solidity实现。Solidity是一种面向以太坊虚拟机（EVM）的高级静态类型编程语言，适用于实现链上状态管理、访问控制、事件记录与资金结算逻辑\cite{solidityDocs}。本系统围绕“作品发布—购买授权—收益分账”三个核心业务过程设计合约体系。

其中，\texttt{MusicAccess1155}合约基于ERC-1155多代币标准实现访问凭证。ERC-1155允许在同一合约中管理多种代币类型，每一种\texttt{tokenId}都可以具有独立的元数据、供应量与业务语义\cite{eip1155}。FreeFlow以“一个\texttt{tokenId}对应一首作品的访问凭证”为建模方式：当用户完成购买后，系统向其地址铸造对应\texttt{tokenId}的凭证，用于后续链上访问权校验。ERC-1155标准本身只规定多代币接口与转移规则，购买凭证是否可转让需要由合约额外限制；若系统要求凭证不可转让，则需要在转移逻辑或钩子中禁止非铸造/销毁场景下的转账行为。这样设计的目的是避免凭证在二级市场流转后削弱作品访问控制的有效性。

除访问凭证合约外，系统还设计了\texttt{PlatformHub}与\texttt{RoyaltySplitter}等业务合约。\texttt{PlatformHub}负责统一接收作品发布请求、记录销售参数、处理购买流程并对外提供访问校验入口；在购买过程中，平台手续费保留在\texttt{PlatformHub}侧，而创作者及协作者对应的收益再转入\texttt{RoyaltySplitter}按预设比例提取。上述合约共同构成系统链上业务闭环。为了降低底层标准实现的出错概率，合约开发过程中可复用OpenZeppelin提供的ERC-1155等标准组件与安全工具库，从而减少重复造轮子并提升代码可审计性\cite{openzeppelinContracts}。


\section{音频代理、Range请求与本地缓存}

为改善音频播放体验，FreeFlow桌面端在本地集成音频代理服务。播放器统一访问本地代理接口，代理服务再根据资源来源决定读取本地文件、磁盘缓存文件或远程地址。该架构具有两项直接收益：其一，能够将本地音频、缓存音频与远程音频抽象为统一访问入口，简化播放器实现；其二，能够在代理层集中处理鉴权、缓存命中、分段请求转发与异常恢复等问题。

音频播放场景通常要求支持拖动进度条、断点续播与快速跳转，因此代理服务必须支持HTTP Range请求。根据HTTP语义规范，客户端可以通过\texttt{Range}请求头请求某一资源的字节区间，服务器在支持时可返回\texttt{206 Partial Content}响应，并可通过\texttt{Accept-Ranges}声明其支持字节范围请求\cite{rfc9110}。这意味着播放器在用户拖动进度条时，无需重新下载整个音频文件，而只需请求目标时间段对应的字节区间即可。系统代理层据此实现两类策略：对于普通非Range请求，可采用边播放边写入本地缓存的方式，以便下次复用完整文件；对于Range请求，则优先透传并返回上游的分段响应，以保证随机访问时的实时性。

从实现角度看，Node.js原生HTTP与流（Stream）机制适合处理此类流式转发场景。其请求与响应接口本身支持对大体积消息进行分块传输和流式处理，无需一次性将完整音频载入内存\cite{nodeHttp,nodeStream}。因此，在桌面端通过Node.js实现音频代理，不仅可以降低内存开销，也能够减少重复访问远程IPFS网关带来的延迟，从而提升链上音乐播放的连续性与稳定性。


\section{本章小结}

本章围绕FreeFlow系统实现所依赖的关键技术展开介绍。桌面端采用Electron与React构建，分别提供桌面宿主环境与组件化交互能力；后端采用Node.js、Express与Prisma实现API服务与关系型数据管理；身份认证采用SIWE机制，将系统用户与钱包地址建立可信绑定；资源存储采用IPFS与Pinata，实现音频与元数据的内容寻址和持久化发布；系统在治理与存储层面采用Web2.5协同取舍，将高可信状态留在链上、将高频协同服务留在链下；链上业务采用Solidity与ERC-1155相关合约，实现作品发布、访问凭证发放与收益分账；播放器侧通过本地音频代理、HTTP Range支持与磁盘缓存机制提升在线播放体验。上述技术共同构成了系统需求分析、总体设计与后续实现章节的技术基础。
